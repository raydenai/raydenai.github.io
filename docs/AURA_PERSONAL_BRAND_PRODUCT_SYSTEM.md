# AURA Personal-Brand Website Product System

AURA is not a page generator. It is a controlled production system for premium personal-brand websites: the system begins with a qualified buyer and a defensible point of view, turns approved strategy into an archetype-specific page architecture and wireframe, then compiles content, photography, implementation candidates, QA evidence, and release authorization.

> A site is not complete because it is visually polished. It is complete when the right buyer can understand the thesis, trust the evidence, see the next appropriate step, and complete it without accessibility, performance, claim, or operational risk.

## The quality contract

Every AURA build must satisfy the following ten conditions before release.

| Contract | Required evidence |
|---|---|
| **Buyer clarity** | A named primary buyer, high-stakes moment, private tension, cost of inaction, and explicit exclusion. |
| **Commercial clarity** | A precise offer, delivery model, ideal fit, non-fit, one primary conversion, and only readiness-appropriate secondary conversion. |
| **Point of view** | One-sentence position, distinct thesis, named method, ordered stages, and tangible outputs. |
| **Evidence discipline** | A claim register with permission, scope, placement, source state, and any required caveat. |
| **Architecture choice** | One selected archetype with an approved rationale and rejected alternatives. |
| **Wireframe approval** | Desktop and mobile composition for every page, section intent, CTA, block candidates, copy requirement, proof requirement, photo role, and responsive behavior. |
| **Image direction** | A source/consent state, unique narrative role, desktop/mobile crop requirement, alt-text intent, and publication rule for every image. |
| **Content governance** | Typed JSON and MDX candidates are reviewed, promoted with an approval reference, hashed, backed up, and reversible. |
| **Build quality** | Type, image, sequence, static-document, form, responsive, keyboard, and dependency gates pass. |
| **Release authority** | The dossier binds strategy, claims, assets, policy state, QA evidence, git revision, and authorization state. |

## The production workflow

| Stage | Owner decision | Required output | Release consequence if missing |
|---|---|---|---|
| 00. Intake | Who is the buyer and why now? | Client brief, voice constraints, compliance flags | No architecture approval. |
| 01. Evidence | What can be said and shown? | Evidence register, case permission notes, asset source state | No proof or public results. |
| 02. Strategy | What commercial motion fits? | Selected architecture, rejected alternatives, conversion decision | No page plan. |
| 03. Wireframe | What does the visitor need at each moment? | Annotated desktop/mobile wireframes and section ledger | No content or visual build. |
| 04. Content | What exactly earns the next decision? | JSON page candidates and MDX candidates | No promotion without approval. |
| 05. Photography | What must the visitor see and believe? | Role-based shotlist, prompt packets, image derivatives | No decorative or unlicensed image publication. |
| 06. Build | How does the approved plan become a site? | Typed Astro content, block registry mapping, responsive implementation | No static build. |
| 07. Review | Is it credible, usable, and technically sound? | Claim review, visual QA, keyboard QA, static policy | No release dossier. |
| 08. Release | Is the deployment authorized? | Dossier, promotion manifest, rollback readiness | No production publication. |

## Wireframe contract

Wireframes are **approval artifacts**, not ornamental mockups. A wireframe must be generated for every approved page before copy or styling are finalized.

Each wireframe page contains the following.

| Layer | Required annotation |
|---|---|
| **Page job** | Primary visitor, desired decision, readiness state, primary CTA, secondary CTA only if justified. |
| **Desktop composition** | Grid, section order, dominant visual area, copy area, proof location, CTA placement, and image aspect/crop. |
| **Mobile composition** | Reading order, crop change, horizontal-to-stacked decision, motion reduction, persistent CTA behavior, and touch constraints. |
| **Section job** | Visitor state, block candidates, section purpose, claim IDs, proof requirement, photo role, and copy brief. |
| **Content boundary** | What cannot be claimed, which evidence is required, whether the section stays as an approved placeholder, and who must approve it. |
| **Implementation bridge** | Target Astro block/component, content record type, responsive class strategy, and required QA checks. |

## Canonical wireframe behavior

A wireframe compiler uses the selected architecture as a starting point, then makes client-specific decisions. It must never produce the same generic homepage for every expert.

| Archetype | First visitor decision | Home persuasion spine | Primary wireframe emphasis |
|---|---|---|---|
| Private Signal | Is this discrete, high-trust expertise relevant? | Recognition → private tension → method → permissioned proof → fit → private conversation | Asymmetric portrait / copy composition, private-room context, quiet qualification. |
| Authority + Speaking | Can this speaker create the needed behavior change? | Stakes → authority → talk outcomes → operating reassurance → availability | Stage context, topic architecture, event form. |
| Creator / Education | Is this a learning path worth entering? | Recognition → first value → teachable method → learning proof → program → start here | Content/guide artifact, pathway visualization, low-friction lead capture. |
| Niche Specialist | Does this diagnostic match my operating problem? | Constraint → diagnosis → method → case anatomy → service fit → assessment | Diagnostic artifact, operational context, qualifying form. |
| Manifesto / Movement | Do I identify with this point of view? | Enemy/default → thesis → story → method → real-world relevance → join | Editorial manifesto, mission context, community / application route. |
| Portfolio / IP | Which intellectual-property path is relevant? | Authority map → ventures/IP → context → route selection | Navigable universe, portfolio hierarchy, route CTA. |
| Enterprise B2B | Can this team reduce decision risk before commitment? | Initiative risk → operating constraints → decision method → scoped proof → solution → discovery brief | Buying-committee context, decision ledger, implementation artifact, qualification route. |

## The distinction between a candidate and a site

AURA must keep four states separate:

1. **Generated candidate:** plan, copy, prompt, or content file that requires review.
2. **Approved artifact:** candidate with a named reviewer and evidence status.
3. **Promoted content:** approved JSON/MDX written to the build tree with a manifest and backup.
4. **Authorized release:** static build with all policy, visual, keyboard, and dossier gates passing.

A generated candidate is never a publishing event. A compelling visual is never proof. A passed build is never a live-client authorization without real policy state.
